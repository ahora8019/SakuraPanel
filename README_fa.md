SakuraPanel به‌عنوان یک برنامهٔ بدون سرورِ مبتنی بر Cloudflare طراحی شده است تا مدیریت کاربران، دستگاه‌ها، قالب‌های کانفیگ، کانفیگ‌های تولیدشده، انتشارهای نسخه‌بندی‌شده، اشتراک‌ها و عملیات امنیتی را انجام دهد. اولویت‌های پروژه به‌ترتیب عبارت‌اند از امنیت، پایداری، کارایی، سازگاری و نگهداشت‌پذیری.

## قابلیت‌ها

- **API مبتنی بر Cloudflare Worker** برای برنامه و عملیات مدیریتی مالک.
- **مخازن دادهٔ D1 و مهاجرت‌های SQL افزایشی** برای نگهداری داده‌ها.
- **احراز هویت و مجوزدهی** شامل نقش‌ها، نشست‌ها، بررسی مالکیت و مدیریت نسخهٔ امنیتی.
- **چرخهٔ عمر کانفیگ** شامل تولید مبتنی بر قالب، اعتبارسنجی، تاریخچهٔ نسخه‌ها، انتشار و عملیات بازگشت به نسخهٔ قبلی.
- **چرخهٔ عمر اشتراک** شامل هش‌کردن و چرخش توکن، ایجاد اشتراک، ارائهٔ آن و عیب‌یابی.
- **کنترل‌های امنیتی** شامل محدودیت اندازهٔ درخواست، بررسی مبدأ درخواست برای تغییرات مبتنی بر کوکی، محدودسازی نرخ درخواست، قفل اضطراری و ثبت رویدادهای حسابرسی.
- **مسیرهای عملیاتی** برای بررسی سلامت و آمادگی سرویس.
- **بررسی‌های خودکار** از طریق GitHub Actions.
- **بات تلگرامی استقرار (در برنامه)** که پس از پایدارشدن Core ساخته می‌شود و منطق آن از هستهٔ برنامه جدا می‌ماند.

قابلیت‌های ذکرشده، کد موجود در مخزن را توصیف می‌کنند؛ این موارد به معنی استقرار در محیط عملیاتی یا تأیید مستقل آن نیستند.

## معماری

```text
کاربر / داشبورد مالک
          |
          v
   Cloudflare Worker
          |
          +-- مسیریابی API و اعتبارسنجی
          +-- احراز هویت / RBAC / نشست‌ها
          +-- سرویس‌های کانفیگ و انتشار
          +-- ارائهٔ اشتراک و عیب‌یابی
          +-- محدودسازی نرخ / قفل اضطراری / حسابرسی
          |
          +------------------+
          |                  |
          v                  v
     Cloudflare D1      Cloudflare KV
     داده‌های برنامه    وضعیت قفل اضطراری
```

در طراحی فعلی نیازی به مدیریت یک VPS جداگانه یا سرویس endpoint مستقل نیست. باکت‌های محدودسازی نرخ در D1 ذخیره می‌شوند و از `SECURITY_KV` برای نگهداری وضعیت قفل اضطراری استفاده می‌شود.

## ساختار مخزن

| مسیر | مسئولیت |
| --- | --- |
| `src/index.ts` | نقطهٔ ورود Worker، مسیریابی، محافظت‌های سراسری درخواست و پاک‌سازی زمان‌بندی‌شده |
| `src/api/` | هندلرهای HTTP و رفتار درخواست و پاسخ API |
| `src/core/` | سرویس‌های برنامه، منطق دامنه، عیب‌یابی و ارائهٔ اشتراک |
| `src/models/` | مدل‌های دادهٔ دامنه |
| `src/repositories/` | لایهٔ ذخیره‌سازی D1 و انتزاع‌های مخزن داده |
| `src/security/` | احراز هویت، مجوزدهی، نشست‌ها، محدودسازی نرخ و سخت‌سازی امنیتی |
| `src/templates/` | فهرست قالب‌ها |
| `src/types/` | نوع‌های مشترک TypeScript و اتصال‌های محیط Worker |
| `src/ui/` | پاسخ داشبورد مالک |
| `tests/` | آزمون‌های واحد، یکپارچه‌سازی، امنیت و صحت ساختار پایگاه داده |
| `migrations/` | مهاجرت‌های مرتب‌شدهٔ طرح D1؛ مهاجرت‌های موجود باید تغییرناپذیر تلقی شوند |
| `scripts/` | اسکریپت‌های عملیاتی، از جمله آزمون‌های نهایی محیط عملیاتی |
| `.github/workflows/` | گردش‌کار CI و استقرار با اجرای دستی |
| `docs/` | معماری، قرارداد محیط، نقشهٔ راه و راهنمای عملیات |
| `wrangler.jsonc` | پیکربندی فعال Wrangler برای محیط متصل پروژه |
| `wrangler.example.jsonc` | نمونهٔ پاک‌سازی‌شده از پیکربندی برای مراجعه |

## پیش‌نیازها

- Node.js نسخهٔ 22 (نسخهٔ استفاده‌شده در CI)
- npm
- یک نسخهٔ محلی از مخزن
- حساب Cloudflare، پایگاه دادهٔ D1 و فضای نام KV فقط هنگام پیکربندی یا استقرار یک محیط

توکن‌های API، اسرار نشست، اسرار راه‌اندازی اولیه یا کلیدهای خصوصی را در فایل‌های کد قرار ندهید و در Git ثبت نکنید.

## شروع کار

نصب وابستگی‌ها:

```bash
npm install
```

اجرای بررسی نوع‌ها و آزمون‌های خودکار:

```bash
npm run typecheck
npm test
```

اجرای محلی Worker:

```bash
npm run dev
```

اجرای محلی ممکن است به پیکربندی معتبر Wrangler و bindingهای محلی نیاز داشته باشد. پیش از تنظیم اسرار یا bindingها، [قرارداد محیط Cloudflare](docs/cloudflare-environment.md) را بخوانید.

## بررسی‌های توسعه

| دستور | کاربرد |
| --- | --- |
| `npm run typecheck` | بررسی TypeScript بدون تولید فایل خروجی |
| `npm test` | اجرای مجموعهٔ آزمون‌های Vitest |
| `npm audit --audit-level=high` | بررسی هشدارهای امنیتی وابستگی‌های نصب‌شده |
| `npm run dev` | اجرای سرور توسعهٔ محلی Wrangler |
| `npm run deploy` | اجرای استقرار با Wrangler؛ **تا تأیید مرحلهٔ انتشار اجرا نشود** |

CI ممیزی وابستگی‌ها، بررسی نوع‌ها و آزمون‌ها را اجرا می‌کند. موفقیت CI فقط همین بررسی‌های خودکار را تأیید می‌کند و اثبات نمی‌کند که bindingهای عملیاتی، مهاجرت‌ها، مسیرها یا استقرار زنده به‌درستی کار می‌کنند.

## مسیرهای HTTP

مسیرهای زیر برای بررسی وضعیت برنامه مفیدند:

| مسیر | کاربرد |
| --- | --- |
| `GET /health` | پاسخ سبک برای بررسی سلامت Worker |
| `GET /ready` | بررسی آمادگی وابستگی‌های پیکربندی‌شده و اسرار موردنیاز |
| `GET /owner` | داشبورد مالک |
| `GET /bootstrap` | صفحهٔ راه‌اندازی نخستین مالک |
| `GET /s/{token}` | ارائهٔ عمومی اشتراک؛ توکن یک اعتبارنامه است و باید محرمانه بماند |
| `/internal/*` | APIهای داخلی احراز هویت‌شده؛ عملیات دقیق به متد و مسیر بستگی دارد |

گروه‌های API داخلی، کاربران، دستگاه‌ها، قالب‌ها، کانفیگ‌ها، سازگاری کانفیگ، انتشار نسخه‌های کانفیگ، اشتراک‌ها، عیب‌یابی اشتراک، رویدادهای حسابرسی و عیب‌یابی سیستم را پوشش می‌دهند. برای رفتار قطعی مسیرها، [مرجع HTTP API](docs/api-reference.md)، فایل `src/index.ts` و هندلر متناظر در `src/api/` را بررسی کنید.

## مدل امنیتی

- `AUTH_SECRET` و `BOOTSTRAP_SECRET` را در محل نگهداری اسرار Wrangler یا GitHub نگه دارید، نه در Git.
- از اسرار تصادفی و قوی با طول حداقل ۳۲ نویسه استفاده کنید.
- پاسخ‌های عمومی اشتراک باید خصوصی و غیرقابل ذخیره در کش باشند.
- بررسی مالکیت و نقش، هش توکن، بررسی انقضا و رفتار امن در صورت خطا را حفظ کنید.
- برای دور زدن خطاها، محافظت مبدأ یکسان یا محدودیت نرخ درخواست را تضعیف نکنید.
- مهاجرت‌های SQL را تغییرات دادهٔ محیط عملیاتی بدانید؛ بازگشت نسخهٔ برنامه لزوماً مهاجرت پایگاه داده را برنمی‌گرداند.
- آسیب‌پذیری‌های احتمالی را به‌صورت خصوصی گزارش کنید؛ به [سیاست امنیتی](SECURITY.md) مراجعه کنید.

## سامانهٔ خودکار استقرار (در برنامه)

قرار است یک بات تلگرامی به‌عنوان رابط کنترل‌شده برای استقرار و عملیات SakuraPanel ساخته شود. این قابلیت در مرحله‌ای بعدی اجرا می‌شود: ابتدا باید Core تکمیل و اعتبارسنجی شود و منطق بات استقرار نباید به منطق داخلی Core وابسته باشد.

جریان کاری موردنظر:

```text
Telegram Bot → درخواست استقرارِ احراز و مجازشده → GitHub Actions
             → بررسی‌ها / آزمون‌ها / مهاجرت D1 → استقرار با Wrangler
             → بررسی سلامت → ارسال نتیجه و گزارش‌ها به تلگرام
```

دستورهای پیشنهادی شامل `/deploy`، `/update`، `/status`، `/logs`، `/rollback`، `/health` و `/version` هستند. اجرای عملیات باید فقط برای مالک‌های مجاز امکان‌پذیر باشد، ثبت رویداد شود و از مرحلهٔ تأیید صریح انتشار عبور کند. در صورت شکست، سامانه باید خطا را عیب‌یابی کند و در صورت امن و پشتیبانی‌شده بودن، امکان بازگشت به نسخهٔ قبلی را فراهم کند.

**قاعدهٔ امنیتی:** توکن‌های Cloudflare و سایر اسرار استقرار نباید هرگز در پیام‌های تلگرام ارسال شوند، به‌عنوان ورودی گردش‌کار افشا شوند یا در مخزن Git قرار گیرند. اسرار فقط باید در سامانهٔ مناسب مدیریت اسرار نگهداری شوند. این بخش معماری برنامه‌ریزی‌شده را توضیح می‌دهد و به معنی پیاده‌سازی یا عملیاتی بودن بات نیست.

## سیاست انتشار

SakuraPanel از ترتیب زیر پیروی می‌کند:

1. پیاده‌سازی و بازبینی تغییرات در یک شاخهٔ ویژگی.
2. اجرای CI شامل ممیزی وابستگی‌ها، بررسی نوع‌ها و آزمون‌ها.
3. بازبینی مسیرهای حساس امنیتی و سازگاری مهاجرت‌ها.
4. بررسی پیکربندی و اسرار بدون افشای آن‌ها.
5. تأیید صریح انتشار.
6. اجرای مهاجرت‌ها و استقرار فقط پس از دریافت مجوز.
7. بررسی سلامت، آمادگی، جریان‌های احراز هویت‌شده، گزارش‌ها و آزمون‌های نهایی.

گردش‌کار استقرار GitHub عمداً دستی است. **برای اینکه ببینید تغییر کار می‌کند یا نه، صرفاً استقرار انجام ندهید.** ابتدا آزمایش کنید؛ پس از عبور از معیارهای انتشار پروژه مستقر کنید و بدون بررسی محیط زنده، ادعای استقرار موفق نداشته باشید.

## وضعیت فعلی

- شاخهٔ توسعه: `feat/compatibility-matrix`
- CI: اعتبارسنجی خودکار پیکربندی شده است؛ برای مشاهدهٔ آخرین نتیجه، بخش Actions را بررسی کنید.
- محیط عملیاتی: این تغییر مستندات، استقرار را تأیید نمی‌کند.
- ادغام و استقرار: در این به‌روزرسانی مستندات انجام نمی‌شود.
